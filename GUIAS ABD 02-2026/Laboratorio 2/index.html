Práctica de Laboratorio 2

Gestión de Usuarios, Roles y Permisos en SQL Server

Bienvenido a la práctica fundamental de administración de seguridad en bases de datos. Aprenderás a implementar seguridad integral y el principio de mínimo privilegio en un entorno real.

En la administración de bases de datos relacionales, una de las tareas más críticas es gestionar quién puede entrar al sistema y qué operaciones específicas puede realizar. Una configuración de seguridad adecuada garantiza la confidencialidad, la integridad de los datos y el aislamiento entre diferentes perfiles y aplicaciones.

A lo largo de este laboratorio trabajarás con la base de datos empresarial DB_Gimnasio, la cual almacena clientes y membresías. Sobre este caso de negocio configurarás dos perfiles de acceso completamente distintos con restricciones estrictas de seguridad.

Objetivos de Aprendizaje

Al completar esta práctica universitaria serás capaz de:

  1. Explicar el modelo de seguridad en 3 niveles de SQL Server: principals (identidades), securables (objetos asegurables) y permisos.
  2. Diferenciar un Login de un Usuario: crear un LOGIN a nivel de servidor y un USER a nivel de base de datos vinculado de forma unívoca por su identificador binario (SID).
  3. Aplicar el Principio de Mínimo Privilegio: diseñar una matriz técnica de control de acceso antes de escribir código T-SQL y comprobar el comportamiento de denegado por defecto.
  4. Crear y Administrar Roles: agrupar permisos por perfiles en lugar de concederlos a usuarios individuales, evitando la dispersión de privilegios.
  5. Dominar la precedencia entre GRANT, DENY y REVOKE: comprender técnicamente cómo resuelve SQL Server los permisos efectivos y demostrar por qué REVOKE ≠ DENY.
  6. Auditar y Comprobar Permisos Objetivamente: simular sesiones de usuarios reales mediante suplantación de identidad (EXECUTE AS USER y REVERT) y funciones de metadatos (fn_my_permissions, HAS_PERMS_BY_NAME).

  2. En el panel izquierdo (Object Explorer), navega a Security → Logins → sa, haz clic derecho y selecciona Properties.
  3. En la pestaña Status marca:

    • Login: Enabled
  4. En la pestaña General escribe una contraseña segura y haz clic en OK.

2. Cómo activar la autenticación mixta en Windows

  1. Conéctate usando Windows Authentication.
  2. Haz clic derecho sobre el nombre del servidor en el Object Explorer y selecciona Properties.
  3. En la pestaña Security selecciona SQL Server and Windows Authentication mode y haz clic en OK.
  4. Paso crítico e indispensable: abre services.msc (Servicios de Windows), busca el servicio SQL Server (MSSQLSERVER) y haz clic en Reiniciar. El cambio de modo no surtirá efecto hasta reiniciar el servicio.

Las Tres Preguntas de la Seguridad en SQL Server

Cada vez que una persona o aplicación intenta realizar cualquier acción en SQL Server, el motor de seguridad evalúa tres preguntas fundamentales en estricto orden:

1. Autenticación

¿Quién eres?

Se valida a nivel de servidor mediante un Login (con contraseña de SQL Server o credencial de Windows).

2. Identidad en la BD

¿Puedes entrar a esta base?

El login debe tener asignado un Usuario de Base de Datos en cada base a la que requiera acceso, vinculado por su SID.

3. Autorización

¿Qué puedes hacer?

Se evalúan los permisos directos del usuario y los heredados a través de sus Roles sobre cada recurso específico.

Diagrama 1: Jerarquía del Modelo de Seguridad

Comprende la cadena de decisión de arriba hacia abajo:

1. SERVIDOR (Instancia SQL Server) Ámbito Servidor
¿Quién tiene acceso a la instancia?
Puerto TCP (1434 o 1433), firewall y motor de base de datos. Administrado por sysadmin.
↓
2. LOGIN (Inicio de Sesión) Autenticación
¿Quién puede conectarse al servidor?
Entidad que autentica en master (ej: sa, orange, app_gym). Posee un SID único.
↓
3. BASE DE DATOS (Contenedor Aislado) Ámbito Base
¿A qué bases de datos tiene autorización para ingresar?
Catálogo independiente (ej: DB_Gimnasio). Los logins no pueden entrar a menos que tengan usuario aquí.
↓
4. USUARIO (User de Base de Datos) Identidad Local
¿Quién representa a ese login dentro de esta base de datos?
Identidad local en DB_Gimnasio enlazada al Login por su SID (CREATE USER ... FOR LOGIN).
↓
5. ROL (Perfil de Acceso) Agrupación
¿A qué conjunto de permisos pertenece el usuario?
Contenedor de permisos (ej: db_lectura, db_app). Simplifica y estandariza la seguridad.
↓
6. PERMISOS (Acciones) Autorización
¿Qué acciones específicas puede ejecutar?
GRANT (concede), DENY (bloquea explícitamente), REVOKE (borra decisión previa).
↓
7. SECURABLE (Recurso Protegido) Destino
¿Sobre qué recurso físico o lógico recae el permiso?
Esquema (SCHEMA::dbo), Tabla (dbo.Cliente), Vista, Procedimiento o Columna específica.
Ejercicio 1

Explorar los Principals Existentes en el Servidor y la Base de Datos

Obligatorio Pendiente
Objetivo pedagógico
Identificar mediante consultas T-SQL los principals a nivel de servidor (logins) y a nivel de base de datos (usuarios y roles), comprobando la identidad con la que estás ejecutando la sesión actual.
Concepto previo

Un principal es cualquier entidad que puede solicitar recursos en SQL Server. Los logins existen globalmente en sys.server_principals (en la base master), mientras que los usuarios y roles existen de forma aislada dentro de cada base en sys.database_principals.

Procedimiento paso a paso
  1. Conéctate a SQL Server en SSMS con la cuenta administradora (sa).
  2. Abre una nueva ventana de consulta (Ctrl + N).
  3. Ejecuta el bloque SQL siguiente para inspeccionar los principals en ambos niveles.
Código que debes ejecutar DB_Gimnasio • T-SQL 
-- 1) Principals a nivel de SERVIDOR (Logins que pueden conectarse)
SELECT principal_id, name, type_desc, is_disabled
FROM master.sys.server_principals
WHERE type_desc IN ('SQL_LOGIN', 'WINDOWS_LOGIN')
ORDER BY principal_id;

-- 2) Principals a nivel de BASE DE DATOS (Usuarios y Roles de DB_Gimnasio)
USE DB_Gimnasio;
GO

SELECT principal_id, name, type_desc
FROM sys.database_principals
WHERE type_desc IN ('SQL_USER', 'DATABASE_ROLE')
ORDER BY principal_id;

-- 3) Identidad y contexto de tu sesión actual
SELECT ORIGINAL_LOGIN() AS login_con_que_me_conecte,
       USER_NAME()      AS usuario_activo_en_esta_bd;
Resultado esperado
  • En la primera consulta: lista de logins del servidor mostrando al menos sa con is_disabled = 0.
  • En la segunda consulta: lista de usuarios del sistema en DB_Gimnasio (como dbo, guest, INFORMATION_SCHEMA, sys).
  • En la tercera consulta: login_con_que_me_conecte = 'sa' y usuario_activo_en_esta_bd = 'dbo'.
¿Qué significa este resultado? Confirma que aunque te conectaste al servidor como el login sa, dentro de DB_Gimnasio tu identidad operativa es dbo (database owner). dbo posee control absoluto sobre la base de datos y no está sujeto a restricciones de permisos comunes.
Evidencia requerida: Guarda captura de pantalla de la salida de la tercera consulta mostrando ORIGINAL_LOGIN() y USER_NAME().
Problema frecuente: Si en la segunda consulta ves usuarios de otra base de datos, aseguraste de haber ejecutado USE DB_Gimnasio; GO antes de consultar sys.database_principals.

Diferencia entre Inicio de Sesión (Login) y Usuario de Base de Datos

Uno de los errores más comunes al iniciar en SQL Server es confundir un login con un usuario:

Característica Inicio de Sesión (LOGIN) Usuario de Base de Datos (USER)
¿Dónde vive? A nivel de Servidor (catálogo master.sys.server_principals). A nivel de cada Base de datos (DB_Gimnasio.sys.database_principals).
Función principal Autenticar: comprobar usuario y contraseña para cruzar la puerta del servidor. Autorizar: ser el titular de permisos dentro de las tablas y esquemas de esa base.
Comando de creación CREATE LOGIN [nombre] WITH PASSWORD = '...'; CREATE USER [nombre] FOR LOGIN [nombre];
¿Cómo se vinculan? A través del SID (Security Identifier), una cadena binaria idéntica en ambos objetos. SQL Server nunca enlaza logins con usuarios por el nombre de texto, sino por este SID.
Políticas de Contraseña

¿Qué hace CHECK_POLICY = ON?
Cuando se especifica CHECK_POLICY = ON, SQL Server utiliza la política de contraseñas configurada en Windows o en el dominio correspondiente. No existe una longitud mínima universal exclusiva de SQL Server; este delega la regla al sistema operativo. Para fines de esta práctica utilizaremos contraseñas de al menos 8 caracteres con combinación de mayúsculas, minúsculas, números y símbolos (por ejemplo, UCA@2025).

Ejercicio 2

Crear el Login y el Usuario del Perfil de Analítica (orange)

Obligatorio Pendiente
Objetivo pedagógico
Crear el login orange en el servidor con políticas de expiración para cuenta de usuario humano, asignarle su usuario en DB_Gimnasio y verificar la vinculación exacta de sus SIDs.
Concepto previo

orange representa a una persona del equipo de analítica de datos. Al ser un usuario humano, se configura con CHECK_EXPIRATION = ON para que el sistema le exija rotar periódicamente su clave.

Procedimiento paso a paso
  1. Posiciónate en master y crea el login orange.
  2. Cambia el contexto de base de datos a DB_Gimnasio y crea el usuario para ese login.
  3. Ejecuta la consulta con JOIN entre master.sys.server_principals y sys.database_principals comparando los SIDs.
Código que debes ejecutar SQL Server • T-SQL 
-- 1) Crear el login a nivel de SERVIDOR (en master)
USE [master];
GO

CREATE LOGIN [orange]
WITH PASSWORD = N'UCA@2025',
     CHECK_POLICY = ON,
     CHECK_EXPIRATION = ON;
GO

-- 2) Crear el usuario dentro de DB_Gimnasio
USE DB_Gimnasio;
GO

CREATE USER [orange] FOR LOGIN [orange];
GO

-- 3) Comprobación del vínculo binario mediante el SID
SELECT s.name AS login_servidor,
       u.name AS usuario_bd,
       s.sid  AS sid_servidor,
       u.sid  AS sid_usuario
FROM master.sys.server_principals s
JOIN DB_Gimnasio.sys.database_principals u ON s.sid = u.sid
WHERE s.name = 'orange';
Resultado esperado

Una fila donde login_servidor = 'orange', usuario_bd = 'orange' y los valores de sid_servidor y sid_usuario son exactamente idénticos (ej: 0x03816B...).

¿Qué significa este resultado? Demuestra de manera tangible que SQL Server no asocia el usuario por su nombre textual, sino que utiliza el SID para saber que cuando alguien inicie sesión como orange, dentro de DB_Gimnasio asumirá los derechos del usuario local homónimo.
Evidencia requerida: Guarda captura de pantalla del resultado de la consulta de verificación de SIDs vinculados.
Problema frecuente: Si recibes Error 15023 (User already exists), significa que ejecutaste el script de usuario más de una vez. No es crítico: continúa al siguiente paso.

Profundización El problema de los usuarios huérfanos (Orphaned Users)

Si restauras un respaldo (.bak) de DB_Gimnasio en otro servidor SQL Server, los usuarios viajarán dentro de la base de datos con sus SIDs originales. Sin embargo, en el nuevo servidor los logins aún no existen o tendrán SIDs diferentes. Esto genera un usuario huérfano (Error 15023).

Para detectar y reparar un usuario huérfano en SQL Server se utiliza:

Código de ejemplo (Solo referencia) T-SQL 
-- Detectar usuarios huérfanos en la base actual
SELECT dp.name AS usuario_huerfano, dp.sid
FROM sys.database_principals dp
LEFT JOIN sys.server_principals sp ON dp.sid = sp.sid
WHERE dp.type = 'S' AND sp.sid IS NULL
  AND dp.name NOT IN ('guest', 'INFORMATION_SCHEMA', 'sys');

-- Re-vincular un usuario huérfano con su login en el servidor
ALTER USER [app_gym] WITH LOGIN = [app_gym];

El Principio de Mínimo Privilegio y el “Denegado por Defecto”

El Principio de Mínimo Privilegio (Principle of Least Privilege - PoLP) establece que cada usuario, proceso o programa debe tener acceso únicamente a la información y recursos indispensables para desempeñar su función legítima, ni un permiso más ni un minuto más.

En SQL Server, este principio está implementado en la arquitectura del motor mediante el denegado por defecto (Default Deny):

Regla base: Cuando creas un usuario en una base de datos, solo recibe automáticamente el permiso CONNECT. Absolutamente todo lo demás está denegado por defecto hasta que un administrador ejecute un GRANT explícito.
Ejercicio 4

Comprobar el “Denegado por Defecto” y Diseñar la Matriz de Permisos

Obligatorio Pendiente
Objetivo pedagógico
Comprobar experimentalmente mediante suplantación de identidad que un usuario recién creado no puede leer tablas (obteniendo el Error 229 esperado), y definir la matriz formal de permisos requerida para el caso de estudio.
Concepto previo

EXECUTE AS USER = 'orange' le pide a SQL Server que cambie temporalmente el contexto de seguridad de la conexión actual para evaluar permisos como si fuéramos orange. Al finalizar siempre debe ejecutarse REVERT.

Procedimiento paso a paso
  1. Conéctate como administrador (sa) y colócate en DB_Gimnasio.
  2. Ejecuta una suplantación de orange intentando consultar dbo.Cliente.
  3. Observa el mensaje rojo de SQL Server y confirma que es el Error 229.
  4. Retorna al contexto de administrador con REVERT.
Código que debes ejecutar DB_Gimnasio • T-SQL 
USE DB_Gimnasio;
GO

-- 1) Suplantamos la identidad de orange
EXECUTE AS USER = 'orange';

-- 2) Intentamos consultar la tabla Cliente sin tener permisos
SELECT * FROM dbo.Cliente;

-- 3) Restauramos inmediatamente nuestra identidad de administrador
REVERT;
GO

-- 4) Confirmamos que volvimos a ser dbo
SELECT USER_NAME() AS usuario_restaurado;
Resultado esperado: Error controlado
Mensaje 229, Nivel 14, Estado 5, Línea 7
Se denegó el permiso SELECT en el objeto 'Cliente', base de datos 'DB_Gimnasio', esquema 'dbo'.
¿Qué significa este resultado? ¡Este error rojo representa el éxito de la prueba! Demuestra que el usuario orange existe y está autenticado, pero SQL Server bloquea la operación porque ningún permiso ha sido concedido todavía. Esto confirma el funcionamiento real del denegado por defecto.
Diseño de la Matriz de Permisos Técnicos

Antes de escribir cualquier comando de autorización, un DBA diseña una matriz de control de acceso:

Recurso / Objeto Perfil Analítica (db_lectura) Perfil Aplicación (db_app) Justificación de Seguridad
dbo.Cliente GRANT SELECT GRANT SELECT, INSERT, UPDATE Analítica lee; la app registra clientes y modifica datos de contacto.
dbo.Membresia GRANT SELECT GRANT SELECT, INSERT, UPDATE Analítica calcula retención; la app crea membresías y actualiza planes.
DELETE en dbo.Cliente Denegado por defecto DENY DELETE explícito Defensa en profundidad: una app nunca debe purgar clientes; se desactivan.
ALTER en esquema dbo Denegado por defecto DENY ALTER explícito Previene ataques de inyección SQL que intenten alterar o truncar estructuras DDL.
Evidencia requerida: Guarda captura de pantalla del Error 229 obtenido al ejecutar la consulta bajo orange.

¿Qué es un Rol y Por Qué se Utiliza?

Un rol en SQL Server es un principal contenedor que agrupa permisos bajo un perfil operativo. Funciona exactamente igual a un grupo de usuarios en un sistema operativo o un perfil de puesto en una empresa:

  • Los permisos se otorgan directamente al rol (ej: db_lectura o db_app).
  • Los usuarios se convierten en miembros del rol y heredan automáticamente todos sus permisos.
  • Cuando un nuevo empleado se incorpora o un desarrollador crea una nueva réplica, basta con agregarlo al rol en una sola línea.
  • Regla de oro de seguridad: Nunca asignes permisos tabla por tabla directamente a cuentas de usuario individuales. Siempre utiliza roles.
Tipo de Rol Ámbito Ejemplos Frecuentes Uso
Roles Fijos de Servidor Instancia sysadmin, securityadmin, serveradmin Mantenimiento general del motor. Predefinidos por SQL Server.

Los Tres Comandos de Autorización

Para cada combinación de principal + permiso + objeto asegurable, SQL Server registra una entrada en el catálogo de seguridad. Tres comandos administran ese registro:

Comando Qué hace en SQL Server Analogía del Mundo Real
GRANT Crea una entrada que concede el permiso de forma explícita. Concesión activa: Otorga el derecho explícito de acceso al objeto.
DENY Crea una entrada que prohíbe taxativamente la acción. Tiene prioridad frente a cualquier GRANT que el usuario reciba directa o indirectamente. Bloqueo restrictivo: Prohíbe explícitamente el acceso; anula cualquier concesión heredada o directa.
REVOKE Elimina una entrada previa de GRANT o de DENY (borrador). No prohíbe nada por sí mismo. Neutralización: Elimina un permiso previamente concedido o denegado, regresando al estado por defecto.
Regla fundamental: REVOKE ≠ DENY

Un error conceptual grave es creer que REVOKE es lo opuesto a GRANT. Si un usuario pertenece al rol db_lectura y ejecutas REVOKE SELECT FROM usuario;, el usuario seguirá pudiendo leer, porque REVOKE solo buscó si había un permiso concedido directamente al usuario (no encontró nada que borrar) y el usuario sigue recibiendo el permiso a través de su rol. Para garantizar que no pueda leer, se debe aplicar un DENY explícito.

Diagrama 2: Árbol de Decisión de Permisos Efectivos

Cuando un usuario intenta ejecutar una instrucción SQL, el motor evalúa esta cadena en orden estricto:

1
¿El usuario es sysadmin o el propietario del objeto (dbo)?

SÍ: Acceso PERMITIDO de forma absoluta. SQL Server omite cualquier revisión de permisos.

2
¿Existe al menos un DENY explícito en el usuario o en cualquiera de sus roles?

SÍ: Acceso DENEGADO (Bloqueo inmediato).

Aclaración técnica: Como regla general, DENY tiene prioridad sobre GRANT. Sin embargo, SQL Server posee algunas excepciones históricas relacionadas con permisos a nivel de columna. Para los ejercicios principales de este laboratorio y el diseño estándar de seguridad, la regla general de bloqueo inmediato se cumple taxativamente.
3
¿Existe al menos un GRANT en el usuario, en sus roles o sobre el esquema?

SÍ: Acceso PERMITIDO. El usuario puede realizar la operación.

4
¿No se encontró ningún permiso?

Acceso DENEGADO POR DEFECTO (Default Deny).

Laboratorio de Precedencia Técnica (GRANT vs DENY vs REVOKE)

Obligatorio Pendiente
Objetivo pedagógico

Matriz de Precedencia y Evaluación de Permisos Interactivo

Haz clic en cada etapa para ver cómo cambia el permiso efectivo de usuario_demo sobre dbo.Cliente:

Etapa / Acción Permiso en Rol (rol_demo) Permiso en Usuario (usuario_demo) Resultado Efectivo Explicación Técnica
Paso 2: Estado Inicial Ninguno Ninguno 0 (Denegado) Denegado por defecto: no hay ningún permiso concedido.
Paso 3: GRANT al rol GRANT SELECT Ninguno 1 (Permitido) El usuario hereda la llave (GRANT) de su membresía en el rol.
Paso 4: DENY al usuario GRANT SELECT DENY SELECT 0 (Bloqueado) El candado (DENY) tiene prioridad sobre la llave heredada.
Paso 5: REVOKE del DENY GRANT SELECT Ninguno (Borrador) 1 (Permitido) REVOKE borró el candado; la llave del rol vuelve a funcionar.
Paso 6: REVOKE del GRANT Ninguno (Borrador) Ninguno 0 (Denegado) Se borró la llave del rol. Regresa al denegado por defecto.
Script de verificación de precedencia
Código que debes ejecutar DB_Gimnasio • T-SQL 
USE DB_Gimnasio;
GO

-- PASO 1: Preparar escenario temporal
CREATE USER usuario_demo WITHOUT LOGIN;
CREATE ROLE rol_demo;
ALTER ROLE rol_demo ADD MEMBER usuario_demo;
GO

-- PASO 2: Estado inicial (esperado: 0 y 0)
EXECUTE AS USER = 'usuario_demo';
SELECT HAS_PERMS_BY_NAME('dbo.Cliente',   'OBJECT', 'SELECT') AS lee_Cliente,
       HAS_PERMS_BY_NAME('dbo.Membresia', 'OBJECT', 'SELECT') AS lee_Membresia;
REVERT;
GO

-- PASO 3: GRANT al rol (esperado: 1)
GRANT SELECT ON dbo.Cliente TO rol_demo;
GO
EXECUTE AS USER = 'usuario_demo';
SELECT HAS_PERMS_BY_NAME('dbo.Cliente', 'OBJECT', 'SELECT') AS lee_Cliente;
REVERT;
GO

-- PASO 4: DENY directo al usuario (esperado: 0)
DENY SELECT ON dbo.Cliente TO usuario_demo;
GO
EXECUTE AS USER = 'usuario_demo';
SELECT HAS_PERMS_BY_NAME('dbo.Cliente', 'OBJECT', 'SELECT') AS lee_Cliente;
REVERT;
GO

-- PASO 5: REVOKE del DENY (esperado: 1)
REVOKE SELECT ON dbo.Cliente FROM usuario_demo;
GO
EXECUTE AS USER = 'usuario_demo';
SELECT HAS_PERMS_BY_NAME('dbo.Cliente', 'OBJECT', 'SELECT') AS lee_Cliente;
REVERT;
GO

-- PASO 6: REVOKE del GRANT del rol (esperado: 0)
REVOKE SELECT ON dbo.Cliente FROM rol_demo;
GO
EXECUTE AS USER = 'usuario_demo';
SELECT HAS_PERMS_BY_NAME('dbo.Cliente', 'OBJECT', 'SELECT') AS lee_Cliente;
REVERT;
GO

-- PASO 7: Limpieza de objetos de prueba
ALTER ROLE rol_demo DROP MEMBER usuario_demo;
DROP ROLE rol_demo;
DROP USER usuario_demo;
GO
¿Qué significa este resultado? Demuestra de forma empírica que REVOKE no es un DENY: REVOKE únicamente borra una regla previa. Al borrar el DENY del usuario en el Paso 5, el usuario volvió inmediatamente a poder leer gracias al GRANT que su rol seguía teniendo.

¿Por Qué Debes Probar Siempre “Como el Usuario”?

Cuando estás conectado en SSMS como el administrador (sa), eres miembro de sysadmin y actúas como dbo dentro de cualquier base de datos.

Regla técnica de verificación: SQL Server NUNCA revisa permisos para sysadmin ni dbo. Si ejecutas una consulta de prueba conectado como sa, la prueba no demuestra absolutamente nada sobre los permisos reales de app_gym o orange.

Para probar de verdad existen dos mecanismos profesionales:

  1. Suplantación de identidad en la sesión: EXECUTE AS USER = 'usuario'; seguido obligatoriamente de REVERT; al terminar.
  2. Funciones de introspección de permisos: HAS_PERMS_BY_NAME() y la función de tabla fn_my_permissions().

Diagnóstico Fundamental: Error 229 vs Error 547

Al realizar pruebas de borrado (DELETE), debes saber interpretar el código de error:

  • Error 229 (Permission Denied): SQL Server bloqueó la consulta en la capa de seguridad. El usuario no tiene permiso para borrar. ¡Es el resultado correcto esperado en este laboratorio!
  • Error 547 (Foreign Key Constraint): SQL Server sí permitió que la consulta pasara la seguridad, pero se detuvo en la capa relacional porque el cliente tiene membresías asociadas. Si aparece 547, la operación alcanzó la comprobación de integridad referencial. Verifique si olvidó EXECUTE AS o si el usuario recibió accidentalmente el permiso correspondiente.

📌 Distinción Fundamental de Términos (¡No confundir LOGIN con USER!):
LOGIN → Servidor (master, SID de instancia)
USER tradicional → Base de datos + Mapeo a LOGIN

ROLE → Agrupación lógica de permisos

1. ¿Qué es una base de datos autocontenida?

En el modelo tradicional de SQL Server, una base de datos tiene una fuerte dependencia de la instancia donde reside: los usuarios dependen de Logins almacenados en la base de sistema master, y la configuración de collation o metadatos depende de opciones globales del servidor.

Una base de datos parcialmente contenida (autocontenida) es aquella diseñada para reducir dependencias respecto a la instancia de SQL Server. Al aislar las identidades y ciertas configuraciones dentro del propio archivo de la base de datos, esta gana autonomía y facilita notablemente su portabilidad.

Modelo Tradicional (Dependencia de Instancia)
INSTANCIA SQL SERVER
│
├─► LOGIN (en master con SID)
│ ↓ autentica en servidor
▼
BASE DE DATOS
│
├─► USER (mapeado por SID al Login)
│ ↓ pertenece a
├─► ROLE (roles de BD)
│ ↓ concede
└─► PERMISSION (GRANT / DENY)

El usuario requiere obligatoriamente que exista un LOGIN en el servidor para poder autenticarse.

Modelo Parcialmente Contenido (Autocontenida)
INSTANCIA SQL SERVER
│
│ (solo provee el motor y puerto)
▼
BASE PARCIALMENTE CONTENIDA
│
├─► USER + PASSWORD (Autónomo)
│ ↓ autentica en la BD (sin Login)
├─► ROLE (roles de BD)
│ ↓ concede
└─► PERMISSION (GRANT / DENY)

El usuario se autentica directamente contra la base de datos utilizando sus credenciales internas.

Regla fundamental de contención:

Un usuario contenido reduce la dependencia de un LOGIN del servidor, pero continúa sujeto a los permisos y roles definidos dentro de la base de datos.

2. Diferencia entre LOGIN tradicional y Usuario Contenido

Esta distinción es uno de los conceptos más evaluados en administración de bases de datos. Comparemos los dos códigos:

Flujo Tradicional (2 pasos):
Tradicional Servidor + BD 
-- 1. Nivel Servidor (master)
CREATE LOGIN james
WITH PASSWORD = 'Admin123!';
GO

-- 2. Nivel Base de Datos
USE DB_Gimnasio;
GO
CREATE USER james
FOR LOGIN james;
GO
Flujo Contenido (1 paso directo en la BD):
Contenido Solo en la BD 
-- Requiere que la BD sea PARTIAL
USE pubs;
GO

-- Crea usuario Y define su clave aquí
CREATE USER james
WITH PASSWORD = 'Admin123!';
GO

Explicación técnica:

La instrucción CREATE USER james WITH PASSWORD = '...' es sustancialmente diferente porque crea un usuario contenido con contraseña. No necesita previamente un CREATE LOGIN james. El usuario y sus credenciales se encuentran almacenados y resueltos directamente dentro de la base parcialmente contenida.

El servidor continúa ejecutando SQL Server, pero la autenticación de este usuario se resuelve en el contexto de la base contenida y no mediante un LOGIN equivalente en master.

💡 ¿Para qué sirven las bases contenidas?

El objetivo principal de las bases parcialmente contenidas es reducir dependencias de la instancia. En entornos empresariales modernos (como clústeres de alta disponibilidad AlwaysOn, migraciones a la nube o ambientes multitenant), mover una base de datos tradicional implica un problema clásico:

Base restaurada en Servidor B ──► Usuario existe en la BD ──► ¡LOGIN correspondiente no existe en master (o tiene SID diferente)! ──► Error: "Usuario huérfano"

Con una base parcialmente contenida, el usuario y sus credenciales viajan dentro de la propia base de datos (en su archivo .mdf y backups .bak). Al restaurar la base en otra instancia de SQL Server, el usuario puede conectarse de inmediato sin necesidad de volver a crear o reparar logins en master.

Precisión técnica indispensable: Las bases de datos contenidas reducen dependencias de la instancia. No afirmamos que eliminen absolutamente todas las dependencias ni que la base sea 100% independiente del motor de SQL Server.

4. Paso 1 — Habilitar la autenticación de bases contenidas

Por seguridad, SQL Server viene configurado de fábrica con esta característica deshabilitada a nivel de instancia. Para permitir que cualquier base pueda usar contención, el administrador (sysadmin) debe habilitarla globalmente:

Configuración de Instancia master • T-SQL 
USE master;
GO

-- 1) Activar la opción de autenticación de bases contenidas
EXEC sp_configure 'contained database authentication', 1;
GO

-- 2) Aplicar el cambio inmediatamente en memoria
RECONFIGURE;
GO
Instrucción / Parámetro Significado técnico
sp_configure Procedimiento almacenado del sistema para consultar o modificar opciones globales de configuración del motor SQL Server.
'contained database authentication' Nombre exacto de la opción que controla si el motor permite autenticación de usuarios contenidos en bases con PARTIAL.
1 Valor de activación (1 = Habilitado, 0 = Deshabilitado).
RECONFIGURE Instrucción que actualiza el valor en ejecución (run_value) en el motor sin requerir reiniciar el servicio de SQL Server.
⚠️ Advertencia de Ámbito: Esta configuración afecta a toda la instancia de SQL Server, no únicamente a una base individual. Si esta opción permanece en 0, cualquier intento de crear o alterar una base a CONTAINMENT = PARTIAL fallará con el Error 12824.

Para comprobar que la opción quedó correctamente aplicada en ejecución:

5. Paso 2 — Crear directamente una base de datos autocontenida

Podemos crear una base de datos indicando desde su nacimiento que será parcialmente contenida:

Creación de Base master • T-SQL 
USE master;
GO

CREATE DATABASE prueba
CONTAINMENT = PARTIAL;
GO

En SQL Server existen dos valores relevantes para la cláusula CONTAINMENT:

  • NONE: Base de datos tradicional no contenida (comportamiento predeterminado). Todas las identidades dependen de logins de instancia.
  • PARTIAL: Base de datos parcialmente contenida. Habilita usuarios contenidos con contraseña, collation a nivel de base y reducción de dependencias.
¿Por qué se llama "Parcialmente" contenida y no "Totalmente"?

Se denomina parcialmente contenida porque SQL Server permite reducir muchas dependencias de la instancia, pero todavía pueden existir elementos o funcionalidades que crucen el límite entre la base de datos y el servidor (por ejemplo, el collation de la instancia para tablas temporales compartidas en tempdb, transacciones distribuidas entre bases o llamadas a procedimientos extendidos del sistema operativo).

6. Paso 3 — Convertir una base existente a parcialmente contenida

Si una base de datos ya fue creada previamente con el modelo tradicional (como pubs), no es necesario recrearla desde cero. Podemos modificarla en caliente mediante ALTER DATABASE:

Conversión de Base master • T-SQL 
USE master;
GO

ALTER DATABASE pubs
SET CONTAINMENT = PARTIAL;
GO
ANTES pubs
CONTAINMENT = NONE
──► ALTER DATABASE ──►
DESPUÉS pubs
CONTAINMENT = PARTIAL
⚠️ Aclaración técnica crucial: Ejecutar ALTER DATABASE pubs SET CONTAINMENT = PARTIAL; NO convierte automáticamente a los usuarios tradicionales existentes en usuarios contenidos. La instrucción habilita las capacidades de contención en la base. Los usuarios existentes continúan asociados a sus respectivos logins de servidor.

Profundización opcional: Para transformar un usuario tradicional existente a contenido sin borrarlo, SQL Server proporciona el procedimiento del sistema sp_migrate_user_to_contained.

7. Paso 4 — Crear el usuario contenido con contraseña

Una vez que la base de datos tiene contención parcial activada, podemos crear directamente usuarios con credenciales propias:

Creación de Usuario pubs • T-SQL 
USE pubs;
GO

-- Usuario contenido con contraseña autónoma (sin LOGIN previo en el servidor)
CREATE USER james
WITH PASSWORD = 'Admin123!';
GO
Aviso de Seguridad Académica: La contraseña Admin123! es estrictamente didáctica para este laboratorio. Nunca utilices contraseñas sencillas ni las reutilices en servidores corporativos reales.

🔐 ¿Por qué aquí no usamos CREATE LOGIN?

Porque james es un usuario contenido. Su hash de contraseña y sus atributos de autenticación residen exclusivamente dentro de la tabla de catálogo interna de la base pubs.

Modelo Tradicional:
LOGIN en master ──► USER en BD
(Requiere 2 entidades sincronizadas)
Modelo Contenido:
USER autónomo en la BD
(1 sola entidad sin Login en master)

⚠️ Importante: ¿Cómo debe conectarse un usuario contenido?

Cuando un usuario contenido con contraseña no tiene un Login correspondiente en master, la conexión debe especificar directamente la base de datos destino.

Parámetros de conexión requeridos:
  • Server name: localhost o el nombre de tu instancia SQL Server.
  • Authentication: SQL Server Authentication.
  • User name: james
  • Password: Admin123!
  • Database / Initial Catalog: pubs (o prueba).

En SQL Server Management Studio (SSMS):
1. En la ventana Connect to Server, escribe el usuario y contraseña.
2. Haz clic en el botón Options >> (abajo a la derecha).
3. Selecciona la pestaña Connection Properties.
4. En el campo Connect to database, escribe directamente pubs (en vez de <default>).

¿Por qué es indispensable este paso? Si el cliente intenta conectarse a la base por defecto (master), el servidor buscará a james en sys.server_principals. Al no existir ningún Login con ese nombre allí, rechazará la conexión inmediatamente arrojando Error 18456 (Login failed for user 'james'). SQL Server necesita saber de antemano en qué base de datos debe autenticar a ese usuario contenido.

9. Principio fundamental: AUTENTICACIÓN ≠ AUTORIZACIÓN

Usuario contenido NO significa "Usuario con todos los permisos"

Crear un usuario con CREATE USER james WITH PASSWORD = '...' únicamente resuelve la autenticación (saber quién es el sujeto). NO le concede automáticamente ningún permiso sobre los datos.

El usuario recién creado no puede hacer SELECT, INSERT, UPDATE, DELETE ni ALTER en ninguna tabla hasta que un administrador le asigne permisos de manera explícita o a través de roles.

Asignación Controlada pubs • T-SQL 
USE pubs;
GO

-- Opción A: Agregar al rol de lectura estándar
ALTER ROLE db_datareader ADD MEMBER james;
GO

-- Opción B: Permiso granular específico sobre un objeto (Mínimo Privilegio)
-- GRANT SELECT ON dbo.authors TO james;
-- GO

Principio de Mínimo Privilegio: Que una base sea parcialmente contenida no altera en absoluto la regla de oro: todo usuario debe recibir exclusivamente los permisos estrictamente necesarios para su función.

🔒 Consideración de seguridad y gobierno corporativo

Habilitar bases parcialmente contenidas permite que un usuario con rol de dueño de base de datos (db_owner) pueda aprovisionar usuarios y contraseñas dentro de su base sin requerir la intervención de un administrador de infraestructura (sysadmin). Si bien esto otorga gran agilidad y portabilidad, debe usarse con conciencia: los administradores de sistemas deben auditar periódicamente las bases contenidas y asegurar políticas de contraseñas robustas.

🧪 Experimento de profundización: La base de datos model como plantilla

Una pregunta técnica frecuente entre administradores es: ¿Qué ocurre si intentamos hacer la base de sistema model autocontenida?

¿Qué es la base de datos model?

model es una base de datos del sistema que SQL Server utiliza como plantilla estándar cada vez que se ejecuta una instrucción CREATE DATABASE. Opciones de configuración, tablas o procedimientos que residan en model se copian automáticamente a las nuevas bases creadas posteriormente.

model (opciones + configuración de plantilla)
 │
 └──► CREATE DATABASE nueva_bd ──► hereda opciones de model

Validación experimental en SQL Server:

Siguiendo las mejores prácticas de administración, antes de intervenir cualquier base del sistema debemos conocer y registrar su estado inicial:

1. Registro de Estado Inicial master • T-SQL 
-- Paso 1: Consultar y registrar la configuración original de model
SELECT name, containment, containment_desc
FROM sys.databases
WHERE name = 'model';
GO
Valor original observado: model → containment = 0 (NONE).

A continuación, probemos ejecutar la instrucción de contención sobre model:

2. Prueba de Contención master • T-SQL 
USE master;
GO

ALTER DATABASE model
SET CONTAINMENT = PARTIAL;
GO
Resultado real arrojado por el motor SQL Server:
Msg 12803, Level 16, State 1, Line 3
Containment cannot be enabled for database 'model' because it is a system database.
Msg 5069, Level 16, State 1, Line 3
ALTER DATABASE statement failed.

¿Por qué SQL Server bloquea este cambio con el Error 12803?

SQL Server prohíbe taxativamente activar contención en bases de datos del sistema (master, model, tempdb y msdb). El motor de bases de datos depende de estas instancias para funciones críticas de servidor, servicios de replicación, catálogos compartidos y resolución de tareas de fondo. Habilitar contención en model comprometería la inicialización y el funcionamiento de la propia instancia.

❌ Lo que NO sucede jamás (Principio de No Retroactividad):

Aun en los aspectos y configuraciones donde model actúa como plantilla para nuevas bases de datos, modificar la plantilla NUNCA altera retroactivamente las bases existentes.

Bases existentes (DB_Gimnasio, pubs, ventas) ──► Permanecen en CONTAINMENT = NONE
Cualquier cambio futuro en plantillas ──► ÚNICAMENTE afectaría a bases creadas DESPUÉS (sin alterar el pasado)

Prioridad de la instrucción explícita en CREATE DATABASE

En el diseño de SQL Server, cualquier parámetro explícito indicado en una instrucción CREATE DATABASE tiene prioridad absoluta sobre cualquier configuración por defecto o heredada:

Sintaxis Explícita master • T-SQL 
-- Aunque existieran plantillas con opciones particulares, la sintaxis explícita manda:
CREATE DATABASE prueba_explica
CONTAINMENT = NONE;
GO
⚠️ Cuidado y Responsabilidad Profesional con las Bases de Sistema:

model es una base de datos fundamental para la estabilidad del motor. No debe utilizarse como entorno de experimentación descontrolada en servidores productivos. En entornos de laboratorio, cualquier verificación sobre bases del sistema debe concluir siempre validando que su configuración retorne al estado original.

Verificación de Restauración master • T-SQL

GO

Guía de Seguridad Profesional DBA Best Practices

Buenas Prácticas de Seguridad en SQL Server

En la gestión corporativa de bases de datos, seguir estándares de hardening protege la información frente a accesos no autorizados y amenazas persistentes:

1. Contraseñas Seguras y Políticas de Complejidad

Mantén siempre CHECK_POLICY = ON para obligar al motor a verificar longitud mínima, caracteres especiales y números mediante las políticas del sistema operativo.

2. Rotación Periódica vs Cuentas de Servicio

Usa CHECK_EXPIRATION = ON para personas físicas (como orange) y OFF para aplicaciones (como app_gym) combinándolo con rotación planificada en bóvedas de secretos (como Azure Key Vault o HashiCorp Vault).

3. Principio de Menor Privilegio (PoLP)

Nunca uses cuentas sysadmin o sa para cadenas de conexión de aplicaciones web. Concede estrictamente las tablas que la app consulta.

4. Uso Exclusivo de Roles

Asigna permisos a roles de base de datos y añade a los usuarios como miembros. Esto previene la acumulación de permisos huérfanos y simplifica las auditorías.

5. Defensa en Profundidad

Aun cuando una aplicación no tenga permiso de borrado concedido, refuerza la regla con un DENY DELETE explícito para blindar tablas críticas ante fallos de configuración futuros.

6. No Conceder Permisos a public ni Habilitar guest

El rol public lo comparten automáticamente todos los usuarios. Conceder permisos sobre public abre puertas traseras para cualquier usuario conectado.

7. Gobernanza y Conexión Segura en Bases Parcialmente Contenidas

Al utilizar usuarios contenidos con contraseña, especifica siempre el parámetro Database / Initial Catalog en las cadenas de conexión (evita apuntar a master por defecto). Los administradores de infraestructura deben supervisar las bases con CONTAINMENT = PARTIAL para auditar las cuentas aprovisionadas por db_owner y desactivar contained database authentication si la instancia no requiere este modelo.

Login vs Usuario
1. Creaste el login orange, pero al intentar conectarse en SSMS no puede entrar a la base de datos DB_Gimnasio. ¿Qué falta?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
Falta crear el usuario de base de datos dentro de DB_Gimnasio (CREATE USER orange FOR LOGIN orange;). El login solo autentica la conexión a nivel de servidor. Y aun con el usuario creado, requerirá permisos para leer tablas, porque todo lo demás permanece denegado por defecto.
Precedencia DENY
2. Un usuario es miembro del rol fijo db_datareader y además tiene un DENY SELECT ON dbo.Cliente. ¿Puede leer Cliente?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
No. Como regla general, un DENY explícito tiene prioridad sobre GRANT (con excepciones específicas como ciertos permisos a nivel de columna), sin importar si proviene de un rol de usuario o de un rol fijo como db_datareader. Sí podrá leer las demás tablas de la base de datos que no tengan un DENY.
Naturaleza de REVOKE
3. Ejecutas REVOKE SELECT ON dbo.Cliente FROM orange;. ¿El usuario orange deja de leer la tabla Cliente?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
No. El permiso de lectura de orange no está concedido en su usuario, sino en el rol db_lectura, y además a nivel de esquema (SCHEMA::dbo). REVOKE sobre el usuario no encuentra nada que borrar. Para impedirlo habría que aplicar DENY SELECT ON dbo.Cliente TO orange; o quitarlo del rol.
Contexto EXECUTE AS
4. ¿Por qué la prueba del DELETE de app_gym debe hacerse obligatoriamente con EXECUTE AS USER?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
Porque si ejecutas la consulta conectado como sa, eres sysadmin/dbo y SQL Server omite cualquier evaluación de permisos: la prueba no demostraría nada sobre las restricciones de app_gym.
Ámbito Esquema vs Tabla
5. ¿Qué diferencia práctica existe entre GRANT SELECT ON SCHEMA::dbo y GRANT SELECT ON dbo.Cliente?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
El primero cubre todas las tablas actuales y futuras dentro del esquema dbo (lo comprobamos con dbo.Pago). El segundo cubre exclusivamente la tabla Cliente. Se elige según el nivel de control fino que requiera la política.
TRUNCATE vs DELETE
6. ¿Un DENY DELETE impide vaciar la tabla con TRUNCATE TABLE dbo.Cliente?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
No. TRUNCATE TABLE es una operación DDL que requiere el permiso ALTER sobre la tabla o el esquema, no el permiso de DELETE. Por eso en la práctica aplicamos como defensa adicional DENY ALTER ON SCHEMA::dbo TO db_app;.
Políticas de Expiración
7. ¿Por qué app_gym se creó con CHECK_EXPIRATION = OFF mientras que orange tiene ON?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
Porque app_gym es una cuenta de aplicación. Si su contraseña caducara inesperadamente, el backend web colapsaría de inmediato. Su rotación se realiza de forma planificada. CHECK_POLICY sí se mantiene en ON para garantizar robustez.
Defensa en Profundidad
8. Te piden un perfil que pueda insertar membresías pero nunca modificarlas ni borrarlas. ¿Qué comandos T-SQL utilizarías?
Razona el caso técnico antes de consultar la solución.
Respuesta y Explicación:
GRANT SELECT, INSERT ON dbo.Membresia TO rol; y, como salvaguarda de defensa en profundidad, DENY UPDATE, DELETE ON dbo.Membresia TO rol;. Luego se valida con EXECUTE AS USER comprobando que el INSERT sea exitoso y que UPDATE y DELETE arrojen el Error 229.
Bases Contenidas
9. ¿Cuál es la diferencia principal entre CREATE LOGIN james y CREATE USER james WITH PASSWORD = '...'?
Razona el ámbito de ejecución y dónde se almacenan las credenciales.
Respuesta y Explicación:
CREATE LOGIN james crea una identidad a nivel de instancia/servidor (almacenada en la base de sistema master con su propio SID único). En cambio, CREATE USER james WITH PASSWORD = '...' crea un usuario contenido directamente dentro de una base de datos con CONTAINMENT = PARTIAL; sus credenciales residen exclusivamente en la base de datos y no requiere ningún LOGIN equivalente en master.
Soporte de Contención
10. ¿Por qué CREATE USER ... WITH PASSWORD no funciona de la misma forma en una base de datos tradicional?
Recuerda el requisito técnico de contención en la base de datos.
Respuesta y Explicación:
Porque en una base tradicional (donde CONTAINMENT = NONE), SQL Server delega obligatoriamente la autenticación al nivel de servidor mediante Logins. Si intentas ejecutar CREATE USER ... WITH PASSWORD en una base no contenida, SQL Server arroja el Error 33233: "You can only create a user with a password in a contained database".
CONTAINMENT = PARTIAL
11. ¿Qué hace técnicamente la opción CONTAINMENT = PARTIAL?
Piensa en qué capacidades de aislamiento e identidades se habilitan.
Respuesta y Explicación:
Habilita el modelo de contención parcial en la base de datos. Permite aprovisionar usuarios contenidos con contraseña propia (sin depender de logins en master), resuelve el collation a nivel de catálogo interno y reduce las dependencias respecto a la configuración global de la instancia, facilitando la portabilidad y migración de la base.
sp_configure
12. ¿Qué hace EXEC sp_configure 'contained database authentication', 1; RECONFIGURE;?
Distingue entre configuración de instancia y configuración de base de datos.
Respuesta y Explicación:
Habilita a nivel de instancia global la capacidad de SQL Server para procesar y autenticar bases de datos contenidas. Si esta opción permanece en 0, cualquier intento de crear o modificar una base a CONTAINMENT = PARTIAL fallará con el Error 12824. RECONFIGURE aplica el cambio en memoria inmediatamente sin reiniciar el servicio.
No Retroactividad
13. ¿Modificar la base de datos model cambia retroactivamente las bases de datos que ya existen?
Analiza cómo operan las plantillas en sistemas de gestión de bases de datos.
Respuesta y Explicación:
No, jamás. Las modificaciones en plantillas nunca son retroactivas. Si bases como DB_Gimnasio o pubs ya existían con CONTAINMENT = NONE, conservan exactamente su configuración original inalterada.
Base model de Sistema
14. ¿Qué influencia tiene model sobre bases creadas posteriormente y por qué SQL Server impide alterar su contención?
Recuerda el resultado del Error 12803 obtenido en el laboratorio.
Respuesta y Explicación:
model actúa como plantilla para las nuevas bases creadas con CREATE DATABASE. Sin embargo, SQL Server prohíbe taxativamente habilitar contención en model arrojando el Error 12803 ("Containment cannot be enabled for database 'model' because it is a system database") para proteger la estabilidad del motor y sus servicios internos. Asimismo, cualquier cláusula explícita (como CREATE DATABASE ... CONTAINMENT = NONE) siempre prevalece sobre cualquier plantilla.
Autenticación vs Autorización
15. ¿Un usuario contenido obtiene automáticamente permisos sobre las tablas al ser creado?
Recuerda la diferencia entre saber quién es y saber qué puede hacer.
Respuesta y Explicación:
No, en absoluto. Rige el principio de que AUTENTICACIÓN ≠ AUTORIZACIÓN. Crear un usuario contenido solo valida su identidad; no le otorga permisos de lectura ni escritura. El usuario no podrá consultar ni modificar ninguna tabla hasta que se le asigne explícitamente permisos mediante GRANT o membresía en roles (como db_datareader).
Conexión a BD Contenida
16. ¿Por qué al conectarse con un usuario contenido es obligatorio indicar directamente la base de datos destino en la conexión?
Piensa qué sucede si la conexión intenta ir a la base master por defecto.
Respuesta y Explicación:
Porque el usuario contenido no existe en master ni tiene un Login en la instancia. Si el cliente intenta conectarse a la base por defecto (master), SQL Server busca el login allí, no lo encuentra y rechaza la conexión con el Error 18456 (Login failed). Al especificar Connect to database: pubs (o Initial Catalog), SQL Server sabe en qué base de datos específica debe autenticar las credenciales del usuario.
