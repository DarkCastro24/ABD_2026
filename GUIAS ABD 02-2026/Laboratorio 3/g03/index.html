Auditoría de bases de datos

Administración de Bases de Datos · Ciclo 02-2026 · Laboratorio 3 · Versión 1

En una base de datos, los permisos indican qué operaciones puede realizar una cuenta. La auditoría permite conservar evidencia de las acciones que se hayan elegido para registrar. En este laboratorio configurarás SQL Audit y revisarás los eventos que produce una pequeña aplicación universitaria.

Imagina que el área académica administra reservas de salas de cómputo. Una reserva se consulta, otra se agrega y un registro de prueba se retira. Utilizaremos datos completamente ficticios en una base de práctica para seguir estas acciones y aprender a interpretar los registros.

Al finalizar podrás

  • Distinguir la auditoría de servidor de la especificación de auditoría de base de datos.
  • Registrar SELECT, INSERT y DELETE sobre una tabla.
  • Identificar en un evento su fecha, cuenta, objeto e instrucción.
Idea central. Proteger las cuentas, asignar permisos y auditar acciones son controles que se complementan. La auditoría aporta evidencia para investigar; no reemplaza los permisos ni las copias de seguridad.

Supón que desaparece una reserva de una sala de cómputo. Consultar la tabla confirma que ya no está, pero no explica qué instrucción produjo el cambio. Si la auditoría estaba activa, sus registros pueden ayudarte a ubicar un DELETE, la cuenta asociada y el momento en que ocurrió.

Cuándo ayuda

  • Una eliminación inesperada: permite localizar la operación que debe investigarse.
  • Una consulta a datos sensibles: permite revisar qué cuentas accedieron a una tabla cuando se configuró el registro de esa acción.
  • Un cambio discutido: aporta una instrucción y una hora que pueden contrastarse con otras evidencias.

Contar con registros reduce las suposiciones durante una investigación. Sin una auditoría configurada de antemano, puede ser difícil reconstruir qué cuenta ejecutó una instrucción. Activarla después de un incidente no recupera eventos anteriores.

Ten presente su alcance. Auditar no impide una operación ni restaura los datos. Un registro identifica la cuenta utilizada, pero si varias personas comparten esa cuenta no demuestra cuál de ellas actuó.

Registrar cada acción ocupa espacio y hace más lenta la revisión. Por eso, en este ejercicio observaremos solo una tabla y tres operaciones.

Necesitas una instancia de práctica de SQL Server, SSMS y una conexión autorizada para crear una base de datos y configurar auditorías.

Prepara la carpeta de registros

  1. En el equipo donde se ejecuta SQL Server, crea C:\AuditLogs\ReservasLab03\. Si te conectas a un servidor remoto, la carpeta debe existir en ese servidor.
  2. Abre Administrador de configuración de SQL Server → Servicios de SQL Server. Busca el servicio del motor de tu instancia, por ejemplo SQL Server (MSSQLSERVER), y anota su valor en Iniciar sesión como. Evita confundirlo con SQL Server Agent.
  3. En la carpeta, entra en Propiedades → Seguridad → Opciones avanzadas → Acceso efectivo y comprueba si esa cuenta puede crear archivos y escribir datos. Si no puedes confirmarlo con tu usuario, anota la cuenta y el resultado para revisarlo con el docente. Más adelante podrás verificar el acceso cuando aparezcan los archivos .sqlaudit.

Si usas SQL Server dentro de un contenedor, sustituye la ruta de Windows por una carpeta disponible dentro del contenedor y con permisos de escritura. Utiliza la misma ruta en CREATE SERVER AUDIT y en sys.fn_get_audit_file.

Antes de continuar. Comprueba que no existan objetos anteriores llamados ReservasLab03, AuditoriaReservas o AuditoriaReservasDB en tu instancia. Si ya empezaste el ejercicio, continúa desde el punto correspondiente y evita repetir las inserciones.

Para que un evento termine en un archivo de auditoría se necesitan dos decisiones: dónde guardarlo y qué acciones observar. Estos son los comandos que utilizarás.

ElementoFunciónEn este ejercicio
CREATE SERVER AUDITDefine el destino de los eventos.Archivos .sqlaudit en una carpeta del servidor.
ALTER SERVER AUDIT ... STATE = ONActiva la auditoría de servidor.Permite comenzar a escribir eventos.
CREATE DATABASE AUDIT SPECIFICATIONElige acciones, objeto y usuarios cuyos eventos se registrarán.SELECT, INSERT y DELETE en dbo.ReservasLaboratorio.
sys.fn_get_audit_fileLee los archivos como filas de una consulta.Mostrará hora, cuenta, objeto e instrucción.

La especificación de la base de datos se vincula a una auditoría de servidor existente. Ambos objetos deben estar activos cuando ejecutes las acciones que deseas registrar. GO separa los lotes enviados por SSMS; no es una instrucción T-SQL del motor.

SQL Audit puede observar eventos de servidor, como inicios de sesión y cambios de configuración, o acciones sobre objetos de una base de datos. También admite destinos en los registros Application y Security de Windows. Aquí usaremos archivos para consultarlos con T-SQL.

BY public incluye a los usuarios de la base en el alcance de la especificación. No les concede permisos sobre la tabla: esos permisos se administran por separado. Las opciones CHECK_POLICY y CHECK_EXPIRATION protegen inicios de sesión de SQL Server y pertenecen a otra configuración.

Antes de ejecutar un bloque: identifica qué objeto crea o cambia y revisa los mensajes de SSMS. Si aparece un error, resuélvelo antes de continuar.

1. Creación de la base de datos

ReservasLab03 será una base independiente con reservas ficticias de salas de cómputo. IdReserva identifica cada fila; la fecha, el turno y el estado describen la reserva. La fila 999 es un registro de prueba y la retiraremos después de activar la auditoría.

SQL
USE master;
GO

CREATE DATABASE ReservasLab03;
GO

USE ReservasLab03;
GO

-- Datos ficticios de reservas de salas de cómputo.
CREATE TABLE dbo.ReservasLaboratorio (
    IdReserva INT PRIMARY KEY,
    Sala NVARCHAR(50) NOT NULL,
    FechaReserva DATE NOT NULL,
    Turno NVARCHAR(20) NOT NULL,
    Estado NVARCHAR(20) NOT NULL
);

INSERT INTO dbo.ReservasLaboratorio
    (IdReserva, Sala, FechaReserva, Turno, Estado)
VALUES (1, N'Sala de cómputo A', '2026-10-06', N'Mañana', N'Pendiente'),
       (2, N'Sala de cómputo B', '2026-10-06', N'Tarde', N'Confirmada'),
       (999, N'Sala de cómputo A', '2026-10-06', N'Mañana', N'Registro de prueba');
GO
Comprueba el primer paso. La tabla ReservasLab03.dbo.ReservasLaboratorio debe contener tres filas. Las dos primeras representan reservas válidas y la tercera está marcada como prueba. Todavía no hay una especificación activa para registrar estas inserciones.

2. Creación y activación de la auditoría

Ahora define el destino en el servidor y, dentro de la base, las acciones que quieres observar. Fíjate en que el objeto de servidor y la especificación terminan activados.

SQL
USE master;
GO

-- El objeto de servidor define dónde quedarán los eventos.
CREATE SERVER AUDIT AuditoriaReservas
TO FILE (
    FILEPATH = N'C:\AuditLogs\ReservasLab03\',
    MAXSIZE = 10 MB,
    MAX_FILES = 5
)
WITH (QUEUE_DELAY = 1000, ON_FAILURE = CONTINUE);
GO

ALTER SERVER AUDIT AuditoriaReservas WITH (STATE = ON);
GO

USE ReservasLab03;
GO

-- La especificación elige las acciones sobre la tabla.
CREATE DATABASE AUDIT SPECIFICATION AuditoriaReservasDB
FOR SERVER AUDIT AuditoriaReservas
ADD (SELECT, INSERT, DELETE ON OBJECT::dbo.ReservasLaboratorio BY public)
WITH (STATE = ON);
GO

MAXSIZE = 10 MB limita cada archivo y MAX_FILES = 5 limita la cantidad de archivos sin eliminar automáticamente los anteriores. QUEUE_DELAY = 1000 permite un pequeño retraso en la escritura. Con ON_FAILURE = CONTINUE, las operaciones pueden continuar si falla el registro; por eso comprobarás que los archivos se generen.

Comprueba el segundo paso. Actualiza el Explorador de objetos de SSMS. Busca AuditoriaReservas en Seguridad → Auditorías del servidor y AuditoriaReservasDB en ReservasLab03 → Seguridad → Especificaciones de auditoría de base de datos. Ambos objetos deben estar habilitados.

1. Genera las acciones

Consulta las reservas, registra una nueva y retira el registro de prueba. Antes del DELETE, verifica que su condición seleccione solo IdReserva = 999. Ejecuta el bloque una vez.

SQL
USE ReservasLab03;
GO

-- Revisa las reservas antes de modificar la copia de trabajo.
SELECT IdReserva, Sala, FechaReserva, Turno, Estado
FROM dbo.ReservasLaboratorio
ORDER BY IdReserva;

-- Registra una nueva reserva.
INSERT INTO dbo.ReservasLaboratorio
    (IdReserva, Sala, FechaReserva, Turno, Estado)
VALUES (3, N'Sala de cómputo C', '2026-10-07', N'Mañana', N'Pendiente');

-- Retira únicamente el registro de prueba.
DELETE FROM dbo.ReservasLaboratorio
WHERE IdReserva = 999;

-- Comprueba el estado final de las reservas.
SELECT IdReserva, Sala, FechaReserva, Turno, Estado
FROM dbo.ReservasLaboratorio
ORDER BY IdReserva;
GO
Revisa el resultado. El último SELECT debe mostrar las reservas 1, 2 y 3. La fila de prueba 999 ya no debe aparecer. La reserva nueva corresponde a la Sala de cómputo C.

2. Lee la evidencia

sys.fn_get_audit_file abre los archivos .sqlaudit y devuelve los eventos como filas. Los filtros dejan solo los de la tabla del ejercicio. Usa una conexión administradora de la práctica; en SQL Server 2025 una cuenta sin ese privilegio necesita VIEW SERVER SECURITY AUDIT para consultar la función.

SQL
USE master;
GO

SELECT event_time, action_id, succeeded,
       server_principal_name, database_name,
       schema_name, object_name, statement
FROM sys.fn_get_audit_file(
    N'C:\AuditLogs\ReservasLab03\*.sqlaudit', DEFAULT, DEFAULT)
WHERE database_name = N'ReservasLab03'
  AND schema_name = N'dbo'
  AND object_name = N'ReservasLaboratorio'
ORDER BY event_time DESC;
GO
CampoCómo leerlo
event_timeHora del evento en UTC.
action_idIdentificador de la acción.
server_principal_nameCuenta de servidor asociada.
database_name, schema_name, object_nameBase, esquema y tabla.
statementInstrucción registrada.
succeededPara estas acciones indica el resultado de la comprobación de permisos; no dice cuántas filas cambiaron.

Busca el INSERT de la reserva 3 y el DELETE de la 999. Después revisa la hora y la cuenta. Puede haber más eventos si repetiste consultas. El registro y el estado final de la tabla responden preguntas distintas: SQL Audit no conserva automáticamente una copia anterior y posterior de cada fila.

¿No aparecen eventos? Espera unos segundos y consulta otra vez. Comprueba que los dos objetos estén activos, que las acciones se hayan ejecutado después de activarlos y que el servicio pueda escribir en la carpeta.

Resuelve estas cinco tareas sobre la base ReservasLab03. Guarda el SQL que utilices y comprueba cada resultado antes de continuar. Las salas, fechas y reservas del ejercicio son ficticias.

  1. Consulta focalizada. Muestra las reservas de la Sala de cómputo A. Localiza el evento SELECT correspondiente.
  2. Nueva reserva. Agrega la reserva 4 para la Sala de cómputo B, el 2026-10-07, en turno de mañana y estado Pendiente. Comprueba la fila y busca el evento INSERT.
  3. Corrección de un registro temporal. Inserta una reserva de prueba con IdReserva = 998 y estado Registro de prueba. Elimínala usando WHERE IdReserva = 998. Identifica los eventos de ambas operaciones y confirma que las reservas válidas siguen presentes.
  4. Amplía la auditoría. Desactiva AuditoriaReservasDB, agrega UPDATE sobre OBJECT::dbo.ReservasLaboratorio para public con ALTER DATABASE AUDIT SPECIFICATION y vuelve a activarla. Cambia solo el Estado de la reserva 1 a Confirmada. Verifica la fila y localiza el evento UPDATE.
  5. Explica la evidencia. Escoge dos eventos distintos e indica qué cuenta, tabla, instrucción y hora aparecen. Explica por qué succeeded = 1 no indica cuántas filas modificó una instrucción.
Entrega. Incluye tu SQL, una captura del estado final de la tabla y otra de los eventos que analizaste. Acompáñalas con respuestas breves. Si una instrucción falla, registra el mensaje y cómo lo resolviste.

Conserva los archivos de auditoría hasta entregar tus evidencias. Si se indica detener la práctica, desactiva primero la especificación y después la auditoría de servidor con STATE = OFF.
