Auditoría de bases de datos

Administración de Bases de Datos · Ciclo 02-2026 · Laboratorio 3 · Versión 1

En clase aprendiste que los usuarios necesitan permisos para consultar o modificar una base de datos. Ahora vamos a observar qué ocurre después de conceder esos permisos: ¿cómo podemos saber qué instrucciones se ejecutaron y con qué cuenta? Para responder, configuraremos una auditoría y revisaremos los registros que produce.

Trabajaremos con un caso distinto al de la clase. Imagina que apoyas al personal de una biblioteca universitaria que está preparando su catálogo de libros. Durante una revisión se consultan títulos, se agrega un libro y se elimina una ficha duplicada. Tu tarea será dejar evidencia de esas operaciones y aprender a interpretarla.

¿Qué vas a aprender?

  • Configurar el destino de los registros y elegir las acciones que quieres observar.
  • Relacionar las operaciones SELECT, INSERT y DELETE con sus eventos de auditoría.
  • Explicar qué información aporta un registro y qué conclusiones requieren una comprobación adicional.
Avanza por bloques. Antes de ejecutar cada uno, lee para qué sirve; después, compara lo que obtuviste con el resultado esperado. Si aparece un error, revisa ese paso antes de continuar: los siguientes dependen de él.

Las políticas de contraseñas que estudiaste en clase protegen el acceso, los permisos delimitan las acciones permitidas y la auditoría permite revisar las acciones que hemos decidido registrar. En esta práctica nos concentraremos en ese seguimiento.

Piensa en esta situación: ayer un libro aparecía en el catálogo y hoy ya no está. Al consultar la tabla puedes confirmar que falta, pero ese resultado no explica cómo desapareció. Tal vez alguien eliminó una ficha equivocada o un proceso automático ejecutó una instrucción incorrecta. Una auditoría configurada antes del incidente puede ayudarte a investigar lo que ocurrió.

Situaciones en las que resulta útil

  • Una eliminación inesperada. En la biblioteca, podrías buscar instrucciones DELETE sobre el catálogo y revisar la cuenta y la hora asociadas. Esa información ayuda a localizar la operación que debe investigarse.
  • Una consulta a información sensible. En un sistema académico, puede ser necesario revisar qué cuentas consultaron una tabla de calificaciones. La auditoría aporta evidencia de los accesos que se hayan configurado para registrar.
  • Un cambio que nadie reconoce. Si un precio cambia en una tienda, registrar las instrucciones UPDATE permite revisar cuándo se intentó modificar la tabla y desde qué cuenta. Para conocer los valores anteriores hace falta un mecanismo adicional que conserve ese historial.

¿Qué ventajas obtenemos?

Contar con registros reduce las suposiciones al investigar un problema: tenemos instrucciones, fechas y cuentas que podemos contrastar. También permite revisar si el uso de la base de datos corresponde a las responsabilidades de cada usuario y aportar evidencias cuando una organización necesita demostrar sus controles. Para que esto sea útil, alguien debe revisar los registros y conservarlos durante el tiempo necesario.

¿Qué ocurre si no tenemos auditoría?

Podemos detectar que un dato falta o está equivocado sin disponer de evidencia suficiente para explicar el incidente. Esto retrasa la investigación, dificulta identificar la cuenta involucrada y hace más complicado distinguir un error de trabajo de un uso indebido. Además, las consultas no autorizadas pueden pasar desapercibidas si no contamos con otros controles que las detecten. Activar una auditoría después no reconstruye los eventos que nunca se registraron.

Ten presente su alcance. La auditoría ayuda a investigar; por sí sola no impide una eliminación ni recupera los datos. Seguimos necesitando permisos adecuados y copias de seguridad. Si varias personas comparten una cuenta, el registro identifica esa cuenta, pero no permite asegurar qué persona la utilizó.

Auditar también tiene un costo: los archivos ocupan espacio y registrar demasiados eventos consume recursos y dificulta su revisión. Por eso elegiremos una tabla y unas pocas acciones, en lugar de intentar registrar todo lo que sucede en el servidor.

Antes de crear la auditoría, verifica dos cosas: que el servicio de SQL Server pueda escribir sus archivos en la carpeta elegida y que puedas ejecutar lotes y leer los mensajes de SSMS. Hazlo en la misma instancia de práctica que usarás para el laboratorio.

Lo que necesitas

  • SQL Server 2025 Developer y SQL Server Management Studio (SSMS), según el entorno de la asignatura.
  • Una instancia de práctica en Windows y una conexión autorizada para crear bases de datos y configurar auditorías. Para el laboratorio puede utilizarse una cuenta administradora de esa instancia.
  • Conocimientos básicos de SELECT, INSERT, DELETE y claves primarias.

1. Identifica la cuenta del servicio

  1. En SSMS, mira el nombre del servidor al que te conectaste. Si es una instancia predeterminada, busca SQL Server (MSSQLSERVER). Si te conectaste a una instancia con nombre, por ejemplo .\SQLEXPRESS, busca SQL Server (SQLEXPRESS).
  2. En el equipo donde funciona esa instancia, abre Administrador de configuración de SQL Server y entra en Servicios de SQL Server. Localiza el servicio anterior; no lo confundas con SQL Server Agent ni con SQL Server Browser.
  3. Lee y anota el valor de Iniciar sesión como. Esa es la cuenta que necesita acceso a la carpeta de auditoría. Solo observa este dato; no cambies la cuenta ni detengas el servicio.

2. Comprueba el acceso a la carpeta

  1. En el equipo que ejecuta SQL Server, crea C:\AuditLogs\BibliotecaLab03\ si aún no existe. Si SSMS está conectado a otro equipo, la carpeta debe existir allí, no solo en tu computadora.
  2. En el Explorador de archivos, haz clic derecho sobre la carpeta y entra en Propiedades → Seguridad → Opciones avanzadas → Acceso efectivo. Selecciona la cuenta que anotaste y consulta su acceso efectivo. Según la versión de Windows, el botón puede llamarse Seleccionar un usuario y luego Ver acceso efectivo.
  3. Comprueba que tenga permiso para crear archivos y escribir datos en la carpeta. Si Windows no puede calcular el acceso efectivo, revisa en la pestaña Seguridad los permisos asignados directamente a la cuenta o a un grupo al que pertenezca. Si no puedes confirmarlo con tu usuario, registra el nombre de la cuenta y el resultado mostrado para revisarlo con el docente.
Ejemplo. Si trabajas con la instancia predeterminada y ves NT SERVICE\MSSQLSERVER en «Iniciar sesión como», comprueba el acceso de esa cuenta a C:\AuditLogs\BibliotecaLab03\. Para una instancia con nombre, usa exactamente la cuenta que muestre tu servicio; puede ser diferente. La comprobación final será que, al activar la auditoría más adelante, aparezcan archivos .sqlaudit en esa carpeta.

3. Prueba SSMS, «Resultados», «Mensajes» y GO

  1. En SSMS, selecciona tu conexión y haz clic en Nueva consulta.
  2. Copia el ejemplo completo de abajo y ejecútalo con Ejecutar o F5. No altera ninguna tabla.
  3. Abre la pestaña Mensajes: debe aparecer Lote 1 ejecutado. Luego abre Resultados: la columna BaseActual debe mostrar master.
SQL
USE master;

PRINT N'Lote 1 ejecutado';
GO

SELECT DB_NAME() AS BaseActual;
GO

GO indica a SSMS dónde termina un lote y comienza el siguiente; no es una instrucción T-SQL del motor. Aquí, USE y PRINT forman el primer lote, mientras que SELECT pertenece al segundo. Si aparece un error en «Mensajes», lee su número y texto antes de seguir con la guía.

Antes de empezar. En la práctica usaremos BibliotecaLab03, AuditoriaBiblioteca y AuditoriaBibliotecaDB. Si ya creaste estos objetos, comprueba en qué paso quedaste antes de repetir instrucciones. En Linux o Docker, la ruta y los permisos deben corresponder al servidor o contenedor.

1. Preparar los datos

La biblioteca necesita un catálogo pequeño para esta prueba. Cada libro tendrá un identificador, un título y un precio de referencia para su reposición. Id es la clave primaria: nos permitirá seleccionar una ficha sin depender de su título. Usamos DECIMAL(10,2) para guardar el precio con dos decimales. Los datos son ficticios y solo se utilizarán en el laboratorio.

SQL
USE master;
GO

CREATE DATABASE BibliotecaLab03;
GO

USE BibliotecaLab03;
GO

-- Cada fila representa una ficha del catálogo.
CREATE TABLE dbo.Libros (
    Id INT PRIMARY KEY,
    Titulo NVARCHAR(100) NOT NULL,
    PrecioReferencia DECIMAL(10,2) NOT NULL
);

-- La primera ficha está duplicada en otro catálogo y se retirará.
INSERT INTO dbo.Libros (Id, Titulo, PrecioReferencia)
VALUES (1, N'Introducción a la programación (ficha duplicada)', 25.00),
       (2, N'Fundamentos de bases de datos', 32.50);
GO

Antes de seguir: deberías tener la base BibliotecaLab03 y dos filas en dbo.Libros. Todavía no estamos auditando esta tabla. Las inserciones de este primer bloque preparan el escenario; los eventos que revisaremos se generarán después de activar la auditoría.

2. Configurar y activar la auditoría

Vamos a separar dos decisiones: dónde guardar la evidencia y qué operaciones registrar. Primero crearemos una auditoría de servidor que escriba en archivos. Luego, dentro de nuestra base de datos, crearemos una especificación que vincule esa auditoría con las acciones sobre el catálogo.

ComponenteFunción en la práctica
Server AuditAuditoriaBiblioteca define el destino de los registros: archivos.
Database Audit SpecificationAuditoriaBibliotecaDB selecciona las acciones y la tabla que se auditarán.
Acciones de auditoríaSELECT, INSERT y DELETE: lectura, inserción y eliminación.
SQL
USE master;
GO

-- Define dónde se guardarán los eventos.
CREATE SERVER AUDIT AuditoriaBiblioteca
TO FILE (
    FILEPATH = N'C:\AuditLogs\BibliotecaLab03\',
    MAXSIZE = 10 MB,
    MAX_FILES = 5
)
WITH (QUEUE_DELAY = 1000, ON_FAILURE = CONTINUE);
GO

-- Crear el objeto no lo activa: es necesario encenderlo.
ALTER SERVER AUDIT AuditoriaBiblioteca WITH (STATE = ON);
GO

USE BibliotecaLab03;
GO

-- Define qué acciones se registrarán y sobre qué tabla.
CREATE DATABASE AUDIT SPECIFICATION AuditoriaBibliotecaDB
FOR SERVER AUDIT AuditoriaBiblioteca
ADD (SELECT, INSERT, DELETE ON OBJECT::dbo.Libros BY public)
WITH (STATE = ON);
GO

Observa la cláusula BY public: permite incluir las acciones de los usuarios de la base, ya que todos pertenecen a ese rol. Esto no les otorga permiso para consultar o modificar los libros; esos permisos se administran por separado. También fíjate en STATE = ON: crear los objetos no basta, necesitamos que tanto la auditoría como su especificación estén activas.

Los archivos de esta práctica serán pequeños: MAXSIZE fija 10 MB por archivo y MAX_FILES establece un límite de cinco archivos; no borra los anteriores de forma automática. QUEUE_DELAY = 1000 configura un intervalo de hasta un segundo para entregar los eventos. Si consultas inmediatamente, quizá necesites esperar y volver a leerlos.

Con ON_FAILURE = CONTINUE, las operaciones pueden continuar si falla la escritura de la auditoría. Esto facilita la práctica, pero también explica por qué debemos comprobar que los archivos realmente se estén generando y revisar el espacio disponible.

Comprobación: en el Explorador de objetos de SSMS, actualiza Seguridad → Auditorías del servidor y BibliotecaLab03 → Seguridad → Especificaciones de auditoría de base de datos. Deben aparecer los objetos creados y estar habilitados. Si hay un error de ruta o permisos, resuélvelo antes de continuar.

1. Generar acciones

Ahora vas a simular una revisión del catálogo: primero consultarás los libros, después agregarás un título y finalmente retirarás la ficha duplicada. Antes de ejecutar el DELETE, observa su condición WHERE Id = 1: es la que limita la eliminación a esa ficha. Ejecuta el bloque una sola vez para que las claves y los datos coincidan con el resultado esperado.

SQL
USE BibliotecaLab03;
GO

-- Consultar el catálogo antes de modificarlo.
SELECT Id, Titulo, PrecioReferencia FROM dbo.Libros;

-- Registrar un nuevo título.
INSERT INTO dbo.Libros (Id, Titulo, PrecioReferencia)
VALUES (3, N'Redes de computadoras', 40.00);

-- Retirar únicamente la ficha duplicada.
DELETE FROM dbo.Libros WHERE Id = 1;

-- Revisar cómo quedó el catálogo.
SELECT Id, Titulo, PrecioReferencia FROM dbo.Libros ORDER BY Id;
GO

Revisa el resultado: el primer SELECT debe mostrar las dos fichas iniciales. En el último deben quedar Fundamentos de bases de datos (Id 2, 32.50) y Redes de computadoras (Id 3, 40.00). Hasta aquí comprobaste los datos; ahora vamos a buscar la evidencia de las instrucciones que ejecutaste.

2. Leer las evidencias

SQL Server guarda los eventos en archivos .sqlaudit. La función sys.fn_get_audit_file permite leerlos como filas de una consulta. El asterisco de la ruta incluye los archivos de esa carpeta, y los filtros dejan solo los eventos de nuestra tabla. Usa la conexión administradora de la práctica; en SQL Server 2025, una cuenta sin ese privilegio necesita VIEW SERVER SECURITY AUDIT para consultar esta función.

SQL
USE master;
GO

SELECT event_time, action_id, succeeded,
       server_principal_name, database_name,
       schema_name, object_name, statement
FROM sys.fn_get_audit_file(
    N'C:\AuditLogs\BibliotecaLab03\*.sqlaudit', DEFAULT, DEFAULT)
WHERE database_name = N'BibliotecaLab03'
  AND schema_name = N'dbo'
  AND object_name = N'Libros'
ORDER BY event_time DESC;
GO
CampoCómo interpretarlo
event_timeFecha y hora del evento en UTC; puede diferir de la hora local.
action_idIdentificador de la acción registrada. Relaciónalo con el texto de la instrucción.
server_principal_namePrincipal de servidor asociado a la ejecución.
database_name / schema_name / object_nameBase de datos, esquema y objeto al que se accedió.
statementTexto de la instrucción registrada.
succeededPara estas acciones, indica si pasó la comprobación de permisos; no demuestra que la transacción se haya confirmado ni cuántas filas cambió.

Empieza por la columna statement y busca el INSERT que agregó el libro. Luego revisa su hora y la cuenta asociada; haz lo mismo con el DELETE. Si utilizaste una sola conexión durante la práctica, es normal que aparezca la misma cuenta en ambos eventos. Puedes encontrar más filas de las que esperabas si repetiste consultas o ya habías realizado otras pruebas.

Cuando leas succeeded = 1, recuerda que para estas acciones significa que se superó la comprobación de permisos. Por ejemplo, un DELETE con una condición que no encuentre filas puede superar esa comprobación y no eliminar nada. Por eso revisamos tanto el registro de auditoría como el estado de la tabla. SQL Audit tampoco conserva automáticamente los valores anteriores y posteriores de cada fila.

¿La consulta no devuelve filas? Espera unos segundos y ejecútala de nuevo. Si sigue vacía, comprueba en este orden: que los dos objetos estén habilitados, que hayas realizado las operaciones después de activarlos y que la ruta permita escribir al servicio de SQL Server. Revisa también que los nombres de la base, el esquema y la tabla coincidan con los filtros.

Buenas prácticas

  • Audita acciones y objetos relevantes: registrar todo aumenta el volumen y dificulta la revisión.
  • Restringe el acceso a los archivos, revisa su espacio disponible y define su conservación. Los registros pueden contener información sensible.
  • Aplica el mínimo privilegio: la cuenta administradora facilita este laboratorio, pero no debe ser la conexión habitual de una aplicación.

Ejercicio propuesto

La biblioteca recibió una nueva cotización y necesita ajustar el precio de referencia del libro Fundamentos de bases de datos. Hasta ahora elegimos SELECT, INSERT y DELETE, por lo que aún falta incluir UPDATE. Usa lo que acabas de practicar para ampliar la configuración y dejar evidencia de este cambio.

  1. Desactiva temporalmente AuditoriaBibliotecaDB con ALTER DATABASE AUDIT SPECIFICATION ... WITH (STATE = OFF).
  2. Agrega la acción UPDATE sobre OBJECT::dbo.Libros para public, mediante ALTER DATABASE AUDIT SPECIFICATION ... ADD (...). Vuelve a activar la especificación.
  3. Cambia únicamente el PrecioReferencia del libro con Id = 2 a 35.00. Comprueba el nuevo valor con SELECT y busca la instrucción UPDATE en los registros de auditoría.

Para entregar: guarda el SQL que utilizaste y dos capturas: una con el catálogo actualizado y otra con el evento UPDATE. Acompáñalas con una explicación breve de cómo relacionaste ese evento con tu cambio. Explica también qué configura la auditoría de servidor, qué configura la especificación de la base y por qué succeeded = 1 no indica cuántas filas se modificaron.

Al terminar: si el docente indica detener la práctica, desactiva primero la especificación y después la auditoría de servidor con STATE = OFF. Conserva los archivos hasta entregar las evidencias.
